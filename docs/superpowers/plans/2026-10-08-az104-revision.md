# AZ-104 Revision Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Philip's personal phone-first AZ-104 revision website, with Microsoft-sourced explanations, durable offline study, and a transparent review queue.

**Architecture:** React components call a local application service that coordinates pure study-engine functions and transactional IndexedDB storage. Versioned question packs are separate from application code and enter normal study only after official-source checks and human review. A PWA serves the browser experience; a separate Cloudflare Static Assets Worker hosts the release without modifying Showtime.

**Tech Stack:** React, TypeScript, Vite, Dexie, Ajv, Vitest, React Testing Library, fake-indexeddb, Playwright, vite-plugin-pwa/Workbox, and Wrangler for deployment preparation. Select mutually supported stable versions at execution time, pin the lockfile, and record Node/npm versions; do not install dependencies during this planning stage.

**Spec:** [Accepted product design](../specs/2026-10-08-az104-revision-design.md). Read both documents before execution. This plan supplies implementation details where the design leaves choices open.

## Global Constraints

- Start with no exam date and permit adding or clearing one later.
- No missed-day penalties or compulsory streaks.
- No Showtime resources are modified.
- First release needs no API, D1 database, Azure subscription, or runtime AI.
- Use Microsoft Learn as the primary source for the syllabus, Azure behaviour, commands, limitations, and worked learning material.
- AI-assisted questions remain draft until human review and cannot silently enter ordinary study.
- Do not copy assessment questions, paid banks, or exam dumps. Do not imply Microsoft endorsement.
- Learn sessions offer 5, 10, or 20 unique questions.
- Timed Practice offers 20 or 40 questions when sufficient eligible content exists, plus a shorter available-bank option.
- Proposed defaults are 30 and 60 minutes respectively, editable before starting.
- These are app practice settings, not a replica of Microsoft's exam format or duration.
- Advance manually by default.
- Use at least 48 CSS pixel interactive targets.
- Test 320–430px layouts without horizontal scrolling and desktop layouts without excessively wide text.
- Scoring is exact set equality for selected and correct option IDs. No partial credit.
- Initial repetition intervals: 1, 3, 7, 14, and 30 days.
- Display recent accuracy over the latest 50 scored attempts with the count.
- Show an objective as insufficient evidence until at least five distinct questions have been attempted.
- Display a freshness reminder when a pack has not been checked for 30 days.
- Limit imports to 10 MB and reject unknown future schema versions with an understandable message.
- No account, analytics tracking, public notes, or client secrets in release one.
- No production deployment or paid resources without the user's release approval, as required by the uploaded plan.
- Keep personal backups, credentials, generated assets, and dependency folders out of Git. Update PROJECT_CONTEXT.md, ROADMAP.md, architecture notes, and verification records as work progresses.

## Review Focus

1. Phone backgrounding or reload after a timed deadline: finalise exactly once and retain all previously saved answers (Tasks 5 and 9).
2. Browser quota failure or two tabs submitting together: show unsaved state, prevent duplicate attempts, and preserve the last durable answer (Task 5).
3. Imported source claims, deceptive Microsoft URLs, or source redirects: do not trust supplied review booleans or let an imported item become normal study without evidence checks (Tasks 1, 2, and 10).
4. A corrected answer while an older session is saved: preserve the historical snapshot, display a correction warning, and exclude invalidated content from current proficiency (Tasks 2, 5, and 8).
5. A new service worker during a session, long explanations, or enlarged text: do not reload the session or trap the user in clipped phone controls (Tasks 6 and 11).

## Shared contracts

Task 1 defines `Question`, `Blueprint`, `ContentPack`, `ValidationIssue`, `SourceCheck`, and `ContentTrust`. The Question fields are those in the spec; its type values are `single | multiple`. Reference `checkedAt` is ISO UTC; nullable document dates remain null when unavailable. Add `ContentPack { id, version, blueprintId, checkedAt, questions }`; `SourceCheck { referenceId, canonicalUrl, checkedAt, result: 'checked' | 'unavailable' | 'changed', evidenceSummary }` and `ContentTrust { questionId, revision, sourceCheckedAt, humanReviewedAt: string | null, reviewer: string | null, invalidatedAt: string | null }`.

Task 3 defines `Confidence = 'confident' | 'unsure' | 'guessed' | 'unknown'`, `ReviewItem { questionId, revision, stage: 0|1|2|3|4, dueAt, misconception }`, and `ReviewOutcome { questionId, revision, correct, confidence, occurredAt, isDueAttempt }`.

Task 5 defines `SessionMode = 'learn' | 'timed' | 'draft-preview'`, `Session { id, mode, questionSnapshots, optionOrders, answers, flags, currentIndex, startedAt, deadlineAt: string | null, status: 'active' | 'submitted', submittedAt: string | null, correctionWarnings: QuestionIdentity[] }`, and `Attempt { id, sessionId, questionId, questionRevision, questionSnapshot, selectedOptionIds, confidence, correct, responseMs, submittedAt, mode }`. `answers` is keyed by question ID and stores selected IDs, confidence, and accumulated active response milliseconds. Settings include `examDate: string | null`, `theme: 'light' | 'dark' | 'system'`, `textScale: 1 | 1.2 | 1.4`, and `autoAdvance: boolean` (false by default).

`SessionResult { sessionId, submittedAt, correct, total, attemptIds, domainResults }` is stored with finalisation; each domain result contains domainId, correct, and total. `DatabaseSnapshot` names every table from Task 5. `StartSessionInput` contains mode, selectedQuestions, durationMinutes (null outside timed mode), and releasesReservedIds. `SessionAnswer` contains selectedOptionIds, confidence, and responseMs. Timestamps are ISO UTC strings. Flags are question-ID arrays; optionOrders maps question IDs to option-ID arrays.

`QuestionIdentity` is `{ questionId: string, revision: number }`; never use array positions as identities. Exact runtime types live in their owning modules; callers import them rather than maintaining parallel definitions. API errors use `AppError { code, message, recoverable }` and are displayed by UI, without logging personal answers or notes to external services.

`ProgressSummary` uses `domains` and `objectives` records keyed by their IDs, plus per-mode recent summaries. Each objective record contains distinctAttempts, accuracy, insufficientEvidence, confidentWrongCount, and coverage counts. `BackupValidation` is `{ valid: boolean, backup: BackupV1 | null, issues: ValidationIssue[] }`. Use these shapes consistently in the test assertion anchors below.
